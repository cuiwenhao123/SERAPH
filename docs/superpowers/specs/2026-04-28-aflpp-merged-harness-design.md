# SERAPH AFL++ Merged Harness Design

## Background

SERAPH's current executable Phase 3 path generates one Rust harness source file per target variant, compiles each file as its own small Cargo binary, optionally repairs compile errors, and smoke-runs each binary in one-shot mode.

That shape has been useful for:

- compile-fix isolation
- per-variant runtime diagnosis
- target-level traceability
- easy stdin or file-based smoke execution

However, the current "aflpp" style is only AFL-friendly, not a real AFL++ macro harness. Generated harnesses are ordinary `fn main()` programs that can later be wrapped by AFL++ tooling, but SERAPH does not yet produce:

- a real merged single-target harness per crate
- an AFL++ macro entrypoint
- a DeepSurf-style paired ASan + CmpLog fuzz campaign

The new requirement is therefore not to replace the current one-shot pipeline, but to layer a second-stage merged fuzz target on top of it:

1. generate small case-level harnesses
2. compile/fix/smoke them individually
3. keep only the cases that actually pass one-shot execution
4. merge those passing cases into one crate-level AFL++ harness
5. launch a paired ASan + CmpLog AFL++ campaign against that merged target

## Goals

- Preserve the existing small-case compile-check, fix-loop, and smoke-run workflow.
- Filter harnesses through one-shot execution before they are eligible for merging.
- Merge only passing case harnesses into one real AFL++ target per tested crate.
- Use AFL++ macro-based execution for the merged target rather than plain stdin/file wrappers.
- Support a DeepSurf-style paired fuzz campaign with two AFL++ jobs cooperating on the same target:
  - one ASan-instrumented job
  - one CmpLog-assisted job
- Keep the merged-harness step deterministic and tool-generated rather than LLM-generated.
- Preserve case-level traceability so results can still be mapped back to the original target-centric harnesses.

## Non-Goals

- Do not replace the case-level generation/fix/smoke flow with direct one-shot generation of a single giant harness.
- Do not ask the LLM to emit `afl::fuzz!` directly for first-round case generation.
- Do not run compile-fix against the merged harness as the primary repair unit.
- Do not require a full 24-hour fuzz run as part of development-time verification.
- Do not merge compile-failed or smoke-failed cases into the final AFL++ target.

## Core Design Decision

SERAPH should use a two-stage harness model:

1. **Case stage**
   LLM-generated Rust harness cases remain the unit of generation, compile-fix, and smoke-run.

2. **Merged stage**
   SERAPH automatically synthesizes one crate-level AFL++ harness from the subset of cases that passed one-shot screening.

This preserves the strengths of the current pipeline while adding a true fuzzing target that better matches evaluation practice.

## Design Principles

### 1. One-shot screening stays authoritative

The merged target is downstream of compile-check and smoke-run. Passing one-shot execution is the gate for merge eligibility.

### 2. Merge logic is tool-owned, not model-owned

The LLM should generate case logic only. Registry generation, dispatcher generation, Cargo layout, and AFL++ launch scripting should be fully deterministic and generated by SERAPH.

### 3. Case-level provenance must survive merge

Each selected case in the merged harness must retain:

- original case identity
- original target API identity
- original marker-bearing target call site semantics

This allows later crash reproduction and analysis to map back to the originating case.

### 4. AFL mode is for the merged stage only

SERAPH should continue to use ordinary one-shot Rust binaries for compile-check, fix-loop, and smoke-run. AFL macro execution should only appear in the merged target that is built after screening.

## End-to-End Flow

The new Phase 3 high-level flow becomes:

1. `phase2 retrieve`
2. `phase3 harness-prompt`
3. `phase3 model-response`
4. `phase3 harness-write`
5. `phase3 compile-check`
6. `phase3 fix-loop`
7. `phase3 smoke-run`
8. `phase3 merge-harnesses`
9. `phase3 afl-bootstrap`

The first seven steps remain case-oriented. The last two operate on the crate-level merged target.

## Harness Shape

### Case harness shape

SERAPH should move the canonical generated case shape away from standalone `fn main()` sources and toward callable case modules.

Each generated case should ultimately be represented as a Rust module exposing:

```rust
pub fn run_case(input: &[u8]) {
    // case-specific setup
    // target call with SERAPH markers
}
```

The important behavior contract is:

- the case accepts fuzz bytes as `&[u8]`
- the case contains the factual setup and target call logic
- the target call remains wrapped by SERAPH markers
- the case never owns process entrypoint logic

### One-shot wrapper shape

For compile-check, fix-loop, and smoke-run, SERAPH should generate a tiny deterministic wrapper binary around each case module.

The wrapper should:

- read bytes from stdin or an optional input file path
- call `run_case(&data)`
- remain entirely tool-generated

This wrapper is the executable artifact used for one-shot screening.

### Merged harness shape

After screening, SERAPH should generate one crate-level merged harness containing:

- a case registry
- a dispatcher
- an AFL++ macro entrypoint
- a one-shot fallback entrypoint for local validation when needed

The merged harness should use input prefix bytes as a selector:

- first bytes choose the case index
- remaining bytes are forwarded as payload to the selected case

This preserves a single AFL++ target binary while still exercising many small target-centric paths.

## Workspace Layout

For a crate-scoped workspace, the merged harness artifacts should live under a crate-specific fuzz directory.

Recommended layout:

```text
workspace/
  fuzz/
    <crate_name>/
      cases/
        case_001_01.rs
        case_001_02.rs
      wrappers/
        case_001_01_main.rs
        case_001_02_main.rs
      merged/
        main.rs
        registry.rs
        selected_cases.txt
  _cargo_projects/
    case_001_01/
    case_001_02/
    merged_<crate_name>/
  reports/
    compile_001_01.json
    smoke_001_01.json
    merge_<crate_name>.json
    afl_campaign_<crate_name>.json
```

Notes:

- `cases/` stores LLM-authored case logic
- `wrappers/` stores deterministic one-shot executables used for screening
- `merged/` stores the crate-level AFL++ target sources
- `_cargo_projects/merged_<crate_name>/` stores the merged Cargo project used for AFL builds and local sanity runs

## Prompt Contract Changes

The first-round prompt should no longer ask the model to generate a complete process entrypoint.

Instead, it should ask for case modules whose responsibility is only target reachability logic.

The prompt contract should require:

- Rust code blocks only
- one case per code block
- a public `run_case(input: &[u8])` function
- all target setup and target invocation inside `run_case`
- SERAPH markers around the exact target API call
- no `fn main()`
- no `afl::fuzz!`
- no crate-level harness registry logic

This keeps the LLM focused on the part where semantic reasoning matters, while SERAPH owns the executable shell.

## Compile, Fix, and Smoke Behavior

### Compile-check

Compile-check should continue to operate per case, but the compiled input is the generated wrapper binary for that case rather than the raw case module by itself.

The compile project generator should:

- create a Cargo project for the case
- write the case module into the project
- write a tool-generated wrapper `main.rs`
- build the wrapper binary

### Fix-loop

Fix-loop should continue to repair the case source, not the generated wrapper. The wrapper should be regenerated after each repair attempt.

This keeps repair prompts small and directly tied to the model-authored logic.

### Smoke-run

Smoke-run should execute the per-case wrapper binary using one-shot input.

Passing smoke-run becomes the merge gate. Any case that does not pass smoke-run remains in reports but is excluded from merged-target synthesis.

## Merge Selection Policy

The merge step should read compile and smoke reports and determine a selected set of cases.

Eligibility rule:

- include a case only if its latest compile status is success and its latest smoke status is success

Exclusion rule:

- exclude any compile-failed case
- exclude any smoke-failed case
- exclude any case with missing required reports

The merge step should be deterministic. Given the same reports and same case files, it should produce the same selected set and the same merged target.

## Merge Artifacts

### `selected_cases.txt`

A plain-text list of selected case identifiers in merge order. This is intended for quick manual inspection.

### `merge_<crate>.json`

The merge report should record at least:

- crate name
- selected case list
- excluded case list
- per-excluded-case reason
- merged source paths
- merged Cargo project path
- timestamp

This report becomes the canonical explanation of what was and was not merged.

### `registry.rs`

The registry should expose the ordered selected case table and dispatcher metadata. This file is fully generated by SERAPH.

### `main.rs`

The merged target entrypoint should:

- decode selector bytes
- dispatch to the chosen case
- support AFL++ macro mode
- optionally support one-shot mode for non-AFL sanity validation

## AFL++ Build Model

The merged harness should be the only artifact built with AFL++ instrumentation.

SERAPH should build three merged-target variants from the merged Cargo project:

1. **Regular AFL target**
   Built with standard AFL++ instrumentation and no extra sanitizer or CmpLog mode. This is the binary used as the normal fuzzing target.

2. **ASan target**
   Built with `AFL_USE_ASAN=1`.

3. **CmpLog helper target**
   Built with `AFL_LLVM_CMPLOG=1`.

The important separation is:

- the ASan binary is fuzzed directly by the ASan-oriented job
- the regular binary is fuzzed directly by the CmpLog-oriented job
- the CmpLog binary is referenced through AFL++ `-c <cmplog_binary>` and is not treated as the main execution binary for that job

All three build outputs should have distinct paths recorded in the campaign report.

## AFL++ Launch Model

SERAPH should launch a paired fuzz campaign against the merged target using two AFL++ jobs that share the same campaign directories.

Required shape:

- one ASan-oriented fuzz job against the ASan-instrumented merged binary
- one CmpLog-assisted fuzz job against the regular merged binary while passing `-c <cmplog_binary>` to AFL++

To keep the shared campaign explicit, SERAPH should launch the two jobs as cooperating AFL++ instances over the same corpus and findings root, using an explicit main/secondary pairing such as:

- `-M` for the primary queue-owning instance
- `-S` for the cooperating secondary instance

The specific assignment should be deterministic. Recommended default:

- ASan instance as the primary job
- CmpLog-assisted instance as the secondary job

The launcher should be able to produce both:

- `--dry-run` command rendering
- `--build-only` execution
- a short sanity run for development
- a full 24-hour experiment command line

The implementation should expose duration and pass-through AFL++ arguments, but the canonical evaluation mode should match the DeepSurf-style setup:

- same logical target
- two cooperating AFL++ jobs
- one ASan-instrumented target
- one CmpLog-assisted configuration

## CLI Changes

### New command: `phase3 merge-harnesses`

This command should:

- discover case-level outputs for a crate workspace
- read compile and smoke results
- choose passing cases
- synthesize merged sources and merged Cargo project
- write merge reports

### Updated command: `phase3 afl-bootstrap`

`afl-bootstrap` should be extended from single-harness bootstrapping to merged-target bootstrapping.

Recommended behavior:

- if a merged target exists, prefer it by default
- support dry-run and build-only modes
- build regular, ASan, and CmpLog binaries
- render or launch the paired AFL++ campaign

### Updated unified flow: `run`

When merged-harness mode is enabled, the high-level run path should be:

1. generate cases
2. screen cases through compile/fix/smoke
3. merge passing cases
4. bootstrap the merged AFL++ campaign

The one-shot screening steps remain mandatory before merge.

## Real-Crate Runner Changes

The real crate helper currently assumes one harness source file maps directly to one Cargo binary project. That assumption should be widened to support:

- case modules plus generated wrappers for one-shot screening
- a separate merged project for AFL++ builds

SERAPH should not require the user to manually maintain these projects.

## Error Handling

The merge and AFL stages should fail clearly in the following cases:

- no passing cases are available for a crate
- a selected case file is missing
- the merged Cargo project cannot be generated
- AFL++ tooling is not installed
- ASan or CmpLog build fails

The failure mode should still leave behind structured reports when possible.

Important rule:

- the absence of AFL++ tooling should not invalidate the earlier one-shot screening results

This allows the system to complete case screening and merge synthesis even on machines that cannot immediately launch AFL++.

## Reporting

### Merge report

`merge_<crate>.json` should capture merge selection and output paths.

### AFL campaign report

`afl_campaign_<crate>.json` should capture:

- crate name
- merged target path
- regular AFL binary path
- ASan binary path
- CmpLog binary path
- corpus directory
- findings directory
- rendered build commands
- rendered fuzz commands
- whether the run was dry-run or build-only
- launch timestamp

This report should exist even for dry-run so experiments are reproducible.

## Testing Strategy

### Unit tests

Add focused tests for:

- case-wrapper generation
- merge eligibility filtering
- deterministic selector dispatch mapping
- merged report rendering
- AFL build and launch command construction

### Integration tests

Use fake `cargo afl` and fake `afl-fuzz` binaries to validate:

- one-shot case screening still works
- only passing cases are merged
- the merged Cargo project is synthesized correctly
- ASan and CmpLog builds are both rendered or invoked
- paired AFL++ launch commands are constructed correctly

### Real-crate validation

For real crates, development-time verification should stop at:

- merged target generation
- successful merged build
- short sanity fuzz execution

The 24-hour full campaign is an experiment run, not a unit or CI requirement.

## Migration Notes

This change intentionally shifts the meaning of Phase 3 `aflpp`:

- case generation stays one-shot-friendly for repairability
- final merged execution becomes real AFL++ macro-based fuzzing

Existing docs that describe `aflpp` as "plain Rust binaries with `fn main()`" will need to be updated to reflect the new two-stage interpretation.

## OpenHarness and Research Positioning

This design fits SERAPH's research direction better than either extreme:

- it is more evaluation-realistic than pure one-shot standalone binaries
- it is more repairable and explainable than asking the LLM for one giant fuzz target directly

It also creates a cleaner paper narrative:

1. SERAPH generates many Rust-specific target-centric case harnesses
2. SERAPH screens them through real compile and smoke execution
3. SERAPH merges only executable cases into a real fuzzing target
4. SERAPH evaluates that target under a paired AFL++ campaign

## Implementation Boundary

This spec defines the target behavior and architecture. The implementation plan should break it into at least these code areas:

- prompt and harness output contract changes
- case wrapper and real-crate project generation
- merge command and merged source synthesis
- AFL++ bootstrap upgrades for ASan + CmpLog paired campaigns
- documentation and tests

## Success Criteria

The feature is complete when all of the following are true:

- SERAPH can still generate, compile-fix, and smoke-run small case harnesses
- only one-shot passing cases are selected for merge
- SERAPH can synthesize one merged harness per crate from selected cases
- the merged harness uses an AFL++ macro-based entrypoint
- SERAPH can build regular, ASan, and CmpLog variants of the merged target
- SERAPH can render and launch a paired AFL++ campaign against the merged target
- dry-run and build-only workflows remain available
- automated tests cover the new selection, merge, and launch behavior
